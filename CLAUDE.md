# Secure Reconnaissance Rover — FPGA Graduation Project

Project brief for Claude Code. Read this fully before writing any code.

---

## 1. Goal

A rover streams live video from places where it might be intercepted, hijacked or captured. Nobody can watch the feed, take control of the rover, or extract its keys.

## 2. Threat model

Every feature exists to stop one of these threats. Don't add features that aren't listed here.

| Threat | Protection |
|---|---|
| Wireless signal intercepted | AES-128-GCM encryption of all video |
| Fake commands / hijacking | AES-GCM-authenticated commands + replay counter |
| Replay of recorded traffic after a reboot | Per-session key derived at boot from fresh nonces from both sides, with an authenticated HELLO exchange (§5.2) |
| Spoofed session setup (fake HELLO) | HELLO messages authenticated under K; base reply bound to `N_rover` (§5.2) |
| Rover captured, keys searched | AES key generated by a ring-oscillator PUF, never stored |
| Rover captured, attacker loads their own bitstream to read the PUF | 7-series bitstream encryption with CFG_AES_Only, or documented as a known limitation (§5.5) |
| Rover captured, enrollment path used to dump K | Enrollment is a separate bitstream; the deployed bitstream has no path from K to any pin (§5.3) |
| Rover software hacked | Encryption is inline in FPGA fabric; no CPU on the rover ever sees plaintext |
| Link lost / commands stop arriving | Motor failsafe: stop after ~500 ms without a valid command (§5.7) |

The ESP32 Wi-Fi modules are **untrusted**. They only ever handle ciphertext. WPA2 is still enabled on the Wi-Fi link as a free extra layer; the design does not rely on it.

**Out of scope (state as known limitations in the thesis):** RF jamming / denial of service; traffic analysis (packet sizes, timing and the plaintext `type` field reveal activity such as motion alerts); side-channel and fault attacks on the captured FPGA; helper-data manipulation attacks on the PUF (§5.3); the bitstream attack if Option B is chosen (§5.5).

## 3. System overview

```
ROVER (Cmod A7-35T)                                   BASE (Basys 3)
OV7670 -> capture -> motion detect -> TX buffer -> AES-GCM -> SPI -> ESP32-S3 ~~Wi-Fi~~ ESP32-S3 -> SPI -> AES-GCM decrypt -> chunk buffer -(tag OK)-> frame buffer -> VGA
                                                                                                                  |
motors/servos <- failsafe <- cmd decrypt+verify <- SPI <- ESP32-S3 ~~Wi-Fi~~ ESP32-S3 <- SPI <- AES-GCM encrypt <- button state (every 50 ms)
RO-PUF -> debias -> fuzzy extractor -> hash -> K (rover)                     enrolled K (base, kept in safe location)
At boot: authenticated HELLO exchange -> both sides derive session key K_s = AES_K(N_rover || N_base)
```

### 5.1 Packet format (both directions)

```
| magic (2B) | type (1B) | session_id (3B) | frame_no (2B) | chunk_no (2B) | counter (8B) | ciphertext (N B) | tag (16B) |
```
- Header = 18 bytes. It is authenticated as GCM AAD (not encrypted). AAD is not a multiple of 16 bytes, so AAD padding must be correct (covered by GCM test case 4).
- `type`: 0x01 video, 0x02 snapshot, 0x03 command, 0x04 motion alert, 0x05 HELLO (session setup, §5.2), 0x06 HELLO_REQ (base asks the rover to start a new session)
- `session_id` lets the receiver rebuild the IV and ignore packets from other sessions.
- Video chunk = 2 image lines = 640 bytes of ciphertext. Packet = 674 bytes.
- **Never release unverified plaintext.** The base decrypts each chunk into a 640-byte chunk buffer and commits it to the frame buffer only if the tag passes. The rover executes a command only after its tag passes.

### 5.2 Session setup and nonce rules (critical — never break these)

**Session setup (every boot, both sides):**
1. Rover powers up, regenerates K from the PUF, draws a 64-bit random `N_rover` from the TRNG, sends HELLO(`N_rover`).
2. Base draws a 64-bit random `N_base`, replies HELLO(`N_rover`, `N_base`). The reply echoes `N_rover` so it is bound to this request.
3. **Both HELLOs are authenticated under K** with GMAC (the GCM core with empty plaintext; the nonces go in the AAD):
   - Rover HELLO IV = `0x03 || N_rover (8B) || 0x000000`
   - Base HELLO IV = `0x04 || N_base (8B) || 0x000000`
   - Never use a counter-based IV under K: counters restart at every boot, so they would repeat IVs under the long-term key.
   - A HELLO with a bad tag, or a base reply that doesn't echo the current `N_rover`, is dropped.
4. Both derive `K_s = AES_K(N_rover || N_base)`. All video and commands use `K_s`, never K directly.
5. `session_id` = first 3 bytes of `N_rover`. Counters reset to 0 for each new session.
6. **Key confirmation:** the session is established on each side only after the first packet under `K_s` passes its tag check. If no valid packet arrives within a timeout, restart the HELLO.
7. **Re-handshake:**
   - Rover reboot: the rover always starts with HELLO.
   - Base reboot: the rover doesn't know, so the base sends HELLO_REQ (unauthenticated, rate-limited; it can only trigger a new handshake). The rover also restarts HELLO after ~2 s with no valid command.
   - Traffic recorded in an earlier session fails the tag check because `K_s` differs.

The TRNG (RO jitter) is on **both** boards. A weak TRNG breaks the session scheme and the HELLO IV uniqueness.
- Online health tests: NIST SP 800-90B Repetition Count Test and Adaptive Proportion Test. On failure, block output and raise an error flag.
- Condition raw TRNG bits (e.g. AES-CBC-MAC over several raw blocks) before using them as nonces.

**Nonce rules:**
- 96-bit GCM IV = `direction (1B) || session_id (3B) || counter (8B)`
- `direction`: 0x01 rover→base, 0x02 base→rover (0x03 / 0x04 are reserved for HELLO under K). This guarantees the two directions never reuse an IV under the same key.
- `counter` strictly increases per packet and never repeats under a session key.
- Replay protection:
  - Commands: reject any packet whose counter ≤ the last accepted counter in the current session.
  - Video: same strict rule by default. A sliding window (IPsec-style bitmap) is optional and low priority; UDP rarely reorders on one Wi-Fi hop, and losing a few chunks is acceptable.
- An IV reuse in GCM breaks confidentiality and authentication. Add an assertion in simulation that catches it.

### 5.3 PUF and key handling

- Ring-oscillator PUF: N ROs, compare pairs, frequency counters.
  - **Sizing:** disjoint pairs give N/2 bits, so 640 raw bits needs ~1,280 ROs. Neighbour-chain comparisons give N−1 bits but they are correlated, so don't count them as independent.
  - To get more stable bits per RO, consider 1-out-of-k masking (Suh & Devadas) or configurable ROs (Maiti & Schaumont).
  - Measure ROs in batches, not all at once, to limit self-heating and supply noise.
- RO placement: every RO is an identical macro with fixed placement and routing: LOC/BEL + RLOC constraints, a Pblock, `DONT_TOUCH`, and fixed (locked) routing. Combinational loops are allowed only inside `ro_puf` (`ALLOW_COMBINATORIAL_LOOPS`). Unequal routing makes the PUF output layout-dependent instead of chip-dependent.
- **Bias:** RO-PUF bits are biased, and a code-offset construction with a repetition code leaks far more than n−k bits under bias (Koeberl et al., 2014, "the repetition code pitfall"). Add a debiasing step before the code offset, and compute min-entropy *with* the measured bias.
- Error correction: code-offset fuzzy extractor plus temporal majority voting over several measurements.
  - Phase 0 / simulation: repetition code (simple).
  - Final design: concatenated repetition + BCH code.
  - Choose code parameters so (min-entropy − helper-data leakage) ≥ 128 bits. Document the calculation in `/docs`.
- After correction, **hash** the response to get K (privacy amplification). Reuse the AES core in Davies–Meyer mode.
- Helper data is public and may be stored in rover flash. It is unauthenticated, so helper-data manipulation attacks (Delvaux & Verbauwhede) are a known limitation.
- **Enrollment (once, in the lab):** a **separate enrollment bitstream** generates K and sends it to the base over a wired UART. The base stores it. Then the deployed bitstream is loaded.
  - The deployed bitstream has **no enrollment mode, no jumper and no path from K or K_s to any pin**, debug ILA or UART.
  - The rover never stores K; it regenerates it at every power-up.

### 5.4 Motion detection

- One 76,800-byte frame buffer (BRAM) holding the previous frame.
- Per pixel, as it arrives: read previous, compute `|cur − prev|`, increment counter if `> PIX_THRESH`, write current over previous.
- At frame end: `motion = count > AREA_THRESH`. Both thresholds are parameters.
- Disable or ignore motion detection while the motors are running (the whole image moves).
- Lock the OV7670's auto exposure / auto gain (AEC/AGC) after start-up, so brightness changes aren't counted as motion.
- On motion: send an alert packet, and optionally raise quality or send a snapshot.

### 5.5 Bitstream security

- The PUF's security depends on the bitstream being protected. State this plainly in the thesis.
- The attacker doesn't need our bitstream: the RO placement is documented in the thesis, so they can build their own bitstream with the same PUF layout, read the helper data from flash, and recover K on the captured chip.
- **Option A:** 7-series bitstream encryption + authentication (AES-256 + HMAC) with the key in eFUSE, **and** the CFG_AES_Only eFUSE burned. Without CFG_AES_Only the FPGA still accepts plaintext bitstreams, so encryption alone doesn't help.
  - Consequences: permanent; that board will only ever run bitstreams encrypted with that key. The Cmod has no BBRAM battery. Needs supervisor approval.
  - Once this is done, the eFUSE key protects everything and the PUF adds little on top. Say so in the thesis.
- **Option B (recommended for a lab board):** keep the bitstream unencrypted and state the attack as a known limitation.

### 5.6 Display

- Basys 3 VGA has 4 bits per channel, so the base shows the upper 4 bits of each pixel (16 gray levels). Note this in the report. Entropy tests (§10) use the full 8-bit data, not the VGA output.
- The base frame buffer may store only 4 bits per pixel (~10 BRAM36 instead of ~19).

### 5.7 Commands

- The base sends its current button state every ~50 ms, as a normal encrypted command packet. No ACK and no retransmit: a lost packet is simply replaced by the next one.
- **Failsafe:** the rover stops the motors after ~500 ms without a valid command.

### 5.8 Video rate control and buffering

- The OV7670 delivers frames faster than the link carries them (it outputs ~30 fps in bursts; the link carries 7–10 fps). Handle this explicitly:
  - Lower the camera frame rate via the CLKRC register, and/or drop frames.
  - Keep a TX buffer between capture and AES-GCM. The Cmod's 512 KB external SRAM is the preferred place for a full frame.
- When the ESP32 isn't ready and the buffer is full, **drop whole frames**, never random chunks.

## 6. Coding rules

**Language:** Verilog for all design code (`.v`, Verilog-2001 synthesizable subset, so it works in Vivado, Quartus and open-source tools). SystemVerilog (`.sv`) for testbenches only.

- Start every RTL file with `` `default_nettype none `` and end with `` `default_nettype wire ``, so typos in signal names become errors instead of silent new wires.
- One module per file. File name = module name.
- Sequential logic: `always @(posedge clk)` with non-blocking `<=` only. Combinational logic: `always @(*)` with blocking `=` only. Never mix the two in one block.
- Every combinational `always` block assigns a default to every output first, so no latches are inferred. Treat any latch warning from synthesis as an error.
- Explicit bit widths on every constant and signal (`8'd0`, not `0`). Fix every width-mismatch warning.
- Synchronous, active-high reset.
- Infer BRAM from RTL; avoid vendor IP except the clocking primitives (MMCM, ODDR) in the top level. Keep cores vendor-neutral.
- Every module gets a **self-checking testbench** `tb_<name>.sv` that compares against expected values, stops with `$fatal` on any mismatch, and prints `TEST PASSED` at the end.
- Crypto testbenches also check against a **Python golden model** (`cryptography` library) using random vectors generated into files, plus the Wycheproof AES-GCM vectors. The same model is the base for the laptop-base fallback.
- Lint every RTL file with `verilator --lint-only -Wall` when available. Verilator catches width and latch mistakes that Verilog itself lets through.
- Camera PCLK → system clock crossing goes through an async FIFO with Gray-coded pointers. No direct signal crossing between clock domains.
- OV7670 PCLK must go to a clock-capable pin (check the Cmod A7 schematic).
- The ESP32 "ready" GPIO is asynchronous: pass it through a 2-flop synchronizer.
- Use `parameter`s for sizes, thresholds and clock frequencies; `localparam` for derived constants.
- Comment every module with its purpose, ports and latency.

## 7. Resource budget (estimates — confirm with Vivado synthesis)

Target device: `xc7a35tcpg236-1` (20,800 LUTs, 41,600 FFs, 50 BRAM36, 90 DSP).

| Block | LUTs (est.) | BRAM36 (est.) |
|---|---|---|
| AES-128 core, iterative (1 round/cycle) | 1,500–2,500 | 0 |
| GHASH, bit-serial | 400–600 | 0 |
| RO-PUF (~1,280 ROs for disjoint pairs) + debias + fuzzy extractor + hash | 4,000–6,500 | 0–1 |
| RO TRNG + health tests + session KDF / HELLO control | 200–400 | 0 |
| OV7670 SCCB + capture + async FIFO | 300–500 | 1 |
| Motion detection (frame buffer) | 200–300 | ~19 |
| TX buffer (external SRAM controller) | 100–200 | 0 |
| SPI + packetizer + FIFOs | 400–600 | 2 |
| Motor + servo PWM + failsafe | ~150 | 0 |
| **Rover total** | **~7,300–11,800 (35–57%)** | **~23 of 50** |

The PUF line is the least certain. Synthesize `ro_puf` early and re-budget; masking or configurable ROs (§5.3) can cut the RO count.

Base: AES + GHASH + depacketizer + chunk buffer + TRNG + VGA + frame buffer, about 3,000–4,000 LUTs and ~12 BRAM36 (4-bit frame buffer) or ~22 (8-bit).

Throughput check: an iterative AES at 100 MHz takes ~11 cycles per 16-byte block, about 1.1 Gbps. GHASH bit-serial (128 cycles/block) gives ~100 Mbps. Both are far above the ~9.7 Mbps (15 fps incl. headers) needed. The bottlenecks are the SPI link and Wi-Fi, not the crypto.

GCM decryption uses only the forward AES function, so the same encrypt-only `aes128_core` serves both boards.

### Known-answer test vectors

AES-128 (FIPS-197, Appendix C.1):
- Key: `000102030405060708090a0b0c0d0e0f`
- Plaintext: `00112233445566778899aabbccddeeff`
- Ciphertext: `69c4e0d86a7b0430d8cdb78070b4c55a`

AES-GCM (McGrew & Viega, "The Galois/Counter Mode of Operation"):
- Test case 1 (all-zero key, 96-bit zero IV), empty plaintext: tag `58e2fccefa7e3061367f1d57a4e7455a`
- Test case 2 (all-zero key, 96-bit zero IV), plaintext = 16 zero bytes: ciphertext `0388dace60b6a392f328c2b971b2fe78`, tag `ab6e47d42cec13bdf53a67b21257bddf`
- Test case 3: 64-byte plaintext, no AAD. Copy key, IV, plaintext, ciphertext and tag from the official document.
- Test case 4: 60-byte plaintext + 20-byte AAD (both non-block-aligned). Copy values from the official document. This is the case that matches our 18-byte header.

Verify all vectors against the official documents before relying on them.

## 9. Fallbacks (use if a risk hits)

| Problem | Fallback |
|---|---|
| Wireless too slow | 160×120 or lower fps; snapshot-on-motion mode |
| ESP32-S3 SPI slave unreliable | Swap roles: ESP32-S3 = SPI master, FPGA = SPI slave (SCLK oversampled at 100 MHz, ≤ 25 MHz) |
| PUF unstable | Stronger code / more votes; worst case, stored key with the PUF demonstrated separately |
| PUF too large for the LUT budget | 1-out-of-k masking or configurable ROs; or a smaller key-demo PUF with the stored-key fallback |
| Bitstream encryption not allowed | Option B: document the attack as a known limitation (§5.5) |
| Camera bring-up stuck | Use a generated test pattern so the rest of the pipeline keeps moving |
| Not enough BRAM | Use the Cmod's 512 KB SRAM for the frame buffer |
| GCM too complex | AES-CTR + AES-CMAC for authentication |
| No second FPGA | Laptop base station: Python decrypt + display (reuse `/model`) |

## 10. Security and performance tests

1. AES/GCM known-answer tests, random vectors vs the Python model, and Wycheproof vectors in simulation.
2. Wireshark capture of Wi-Fi traffic: rebuilt image is noise. Report entropy (~8 bits/byte), flat histogram, adjacent-pixel correlation ≈ 0.
3. Wrong key at base: packets rejected (tag fail).
4. Bit-flipped packets: rejected, and never displayed.
5. Replayed command packets: ignored, within a session and after a rover reboot.
6. Replayed video packets after a base reboot: ignored.
7. Forged commands from another device: ignored.
8. Forged or replayed HELLO messages: ignored; no session is established.
9. Link loss: motors stop within ~500 ms.
10. PUF: inter-chip Hamming distance ≈ 50%, intra-chip ≈ 0% after correction, across power cycles and temperature; measured bias and min-entropy reported.
11. TRNG: SP 800-90B health tests on hardware, plus basic statistical tests on captured output (e.g. NIST SP 800-22 subset).
12. Benchmarks: FPGA AES throughput and latency vs software AES on a PC/Pi; frame rate; end-to-end latency; power.
13. Optional, only if time allows: Ascon-AEAD128 (NIST SP 800-232, August 2025) core as a benchmark comparison against AES-GCM (area, throughput). Not part of the main design.

## 12. First task
