The whole project

A rover streams live video from places where it might be intercepted, hijacked or captured. All crypto runs in FPGA fabric on both ends, the Wi-Fi modules only ever see ciphertext, and the rover's key comes from its own silicon at every power-up, so nothing secret is stored on it.

What someone on the Wi-Fi can see

One rover video packet, 680 bytes (not to scale). Everything in the untrusted zone sees exactly this, for every packet, at a constant rate. Decided 2026-10-28; built in Phase 3 with the packetizer.

The only readable field that varies is kind, and it only says which key to use: DATA, HELLO or HELLO_REQ. Whether a packet carries video, a snapshot or padding, and whether there was motion, is encrypted. When there is nothing to send, the rover sends an encrypted padding packet in the same slot.

Open points from Phase 0

PUF key size

With the repetition code alone, no RO count that fits this FPGA gives a 128-bit key. The feasible path is a BCH outer code without Von Neumann debiasing, using exact bias accounting (500–1,500 ROs). Needs the supervisor's agreement. Details

Session block too big

session_kdf + hello_fsm use 1,743 LUTs against a 200–400 budget, mostly wide registers kept twice. Fix planned for Phase 3 when the top levels share one GCM engine.

Bitstream security: decided

Option B on all main boards: the own-bitstream attack is documented as a known limitation. If the supervisor agrees and a spare Cmod is available, Option A (eFUSE key + CFG_AES_Only, permanent) is burned on that spare board only, at the end of Phase 6, as a demonstration.

Lint and hardware

Verilator is not installed yet, so the lint rule is still open. No boards bought: Basys 3, Cmod A7-35T, OV7670 without FIFO, 2× ESP32-S3-WROOM-1U.

Inside one round, byte by byte

The 128-bit state as AES sees it: 16 bytes in a 4 × 4 grid, filled column by column (bits [127:120] are byte 0, top-left). Hover or tab to a byte to see which bytes it came from.

Timing diagram

The same block as it would appear in the XSim waveform window. A register changes right after a rising clock edge. Click a column to jump to that cycle.

Latency is 10 edges from accepting start (edge N) to done (after edge N+10). Because busy drops on that same edge, a new block can start at edge N+11: one block every 11 cycles, about 1.16 Gbit/s at 100 MHz.

Timing: at 100 MHz a cycle is 10 ns and Vivado reported +3.385 ns of slack, so the slowest path through one round takes about 6.6 ns. That path starts at a register (state or rk), runs through an S-box, MixColumns or the key XOR chain, the round-10 mux and AddRoundKey, and ends back at state. Doing a whole round in one cycle is what makes that path long; it still fits easily.

rtl/common/ghash.v · inside aes_gcm

ghash

The authentication half of GCM. It folds every block of a message into one 128-bit value by computing Y ← (Y ⊕ X) · H in GF(2128). This core does the multiplication one bit per clock, so it is tiny: 128 clocks per block, which is still about 10× faster than the video needs.

The circuit

Shift-and-add multiplication, like long multiplication on paper but in binary with XOR instead of add. Register a feeds out one bit of (Y ⊕ X) per clock; when that bit is 1, v is XORed into the running sum z. v starts as H and is multiplied by x every clock. Click a block for its Verilog.

Why bit-serial

A full 128 × 128 GF multiplier finishes in one clock but costs thousands of LUTs. This version reuses one row of 128 XOR gates 128 times. The rover needs about 10 Mbit/s; this gives about 100 Mbit/s at 100 MHz for 269 LUTs.

The reduction constant

Shifting v right multiplies it by x. When a 1 falls off the end, the result is reduced by XORing R = e1 00…00, which is the GCM polynomial x128 + x7 + x2 + x + 1 in GCM's reflected bit order. R has four 1 bits, so this costs four XOR gates.

Watch one multiplication, bit by bit

Loaded with GCM test case 2: H = EK(0) for the all-zero key, and the ciphertext block. Step through the 128 clocks. After block 2 (the length block), Y ⊕ EK(J0) is the published tag.

rtl/common/aes_gcm.v · one per board, shared by video, commands, KDF and PUF hash

aes_gcm

Authenticated encryption: one aes128_core makes the keystream in counter mode, one ghash makes the tag over the header and the ciphertext. Empty plaintext gives GMAC, which signs the HELLO messages. An extra ECB mode runs one plain AES block so the key derivation shares this core instead of needing a second AES.

The control state machine

aes_gcm is a sequence of steps: two AES calls for setup, then one GHASH per header block, then for each text block an AES call (keystream) and a GHASH, then the length block. Run a message below and watch the active state move. Click a state for its Verilog.

The datapath

What the state machine drives. One AES core is reused for four jobs, picked by the aes_in mux. One GHASH takes the header, the ciphertext, and finally the length block.

Rule: never release unverified plaintext

When decrypting, out_data comes out block by block before the tag is known. The base therefore writes each 640-byte chunk into a chunk buffer and copies it to the frame buffer only if tag_match = 1 after done. Try “Decrypt + verify” above and flip a bit.

Cost of one video packet

18-byte header (2 AAD blocks) + 646 encrypted bytes (6-byte inner header + 640-byte chunk, 41 text blocks): about 24 + 2×129 + 41×143 + 129 cycles. The testbench measured 6,179 cycles for the earlier 674-byte layout; the extra block adds ~143, so ~6,320 cycles ≈ 63 µs at 100 MHz. At 8 fps the rover needs 960 packets/s, about 6% of this core's time.

rtl/rover/motion_detect.v · rover only

motion_detect

Compares every pixel with the same pixel in the previous frame, as the pixels stream in from the camera. If enough pixels changed by more than a threshold, the frame has motion and the rover sets an encrypted motion flag in the packets that follow, so an eavesdropper can't tell. One pixel per clock, no frame stored twice: the read of the old pixel and the write of the new one share one block-RAM frame buffer.

The pipeline

Five stages, one pixel enters per clock. The frame buffer is split into 19 banks of 4K × 8 (one BRAM36 each). Vivado used 24 BRAMs and missed timing with one big array; the banks fixed both.

When a frame doesn't count

The first frame after reset only fills the buffer. A frame is also ignored while the motors run, and so is the frame after, because its reference was taken while the whole image was moving. The camera's auto exposure gets locked at start-up so brightness changes aren't counted as motion; the demo shows what happens without that.

rtl/rover/puf_keygen.v · ro_puf → puf_debias → fuzzy_extractor → puf_hash

PUF → K

The rover's long-term key K is never stored. At every power-up it is measured from tiny manufacturing differences between ring oscillators on this one chip, corrected for noise, and hashed into 128 bits. A captured rover has no key in memory to read out.

One ring oscillator

A NAND and two inverters in a loop: an odd number of inversions, so it never settles and toggles as fast as the silicon allows. Each copy runs at a slightly different speed. Every one of the 1,280 copies must be placed and routed identically, so that the differences come from the chip, not the layout.

From oscillators to a key

Each response bit compares two oscillators of a pair: which one counted more edges in a 4,096-clock window, majority of 5 tries. Then debiasing, error correction against the helper data, and a hash. Click any block.

Error correction on one block

The repetition code with R = 5, exactly as fuzzy_extractor.v does it. In the lab, the enrollment bitstream reads x and stores only the helper w (how each bit relates to the first). At power-up the reading is a little noisy. Click bits of the power-up reading to add noise.

Why debias

Real RO bits lean toward 0 or 1. Biased bits leak through the helper data. Von Neumann debiasing takes bits in pairs: 01 → keep 0, 10 → keep 1, 00 and 11 → drop. For independent bits, what's kept is 50/50 whatever the bias. The price is throughput.

First 40 raw pairs (green = kept)

Sizing finding

Current build is a demo

Defaults: 1,280 ROs, VN debiasing, rep(5) × 24 blocks. That gives 24 bits of entropy, not 128. The pipeline works: same chip gave the same K over 6 power-ups; another chip gave a different K (49.5% raw bit difference).

Repetition alone can't reach 128 bits

No RO count that fits this FPGA gives a 128-bit key with the repetition code. VN debiasing multiplies the RO count by about 4.5.

Recommended path

Add a BCH outer code, skip VN when the measured bias is within 0.45–0.55, and count the bias exactly in the entropy: 500–1,500 ROs. Needs the supervisor's agreement (docs/puf_entropy.md).

rtl/common/ro_trng.v + trng_health.v · both boards

TRNG

Fresh random nonces for every session. Four free-running ring oscillators drift against the system clock; their XOR, sampled every 64 clocks, is noise. Two health tests watch the raw bits and block the output the moment the source looks broken, because a weak random source would break the session scheme.

The circuit

The oscillators are not in sync with the system clock, so their XOR is passed through a 2-flop synchronizer. The first flop may go metastable; that is part of the noise. Click a block for its Verilog.

Break the source and watch the tests

Feeds bits through the same two tests with the same counters and cutoffs as trng_health.v. No output until the first 1,024-sample window passes; any failure blocks output until reset.

rtl/common/hello_fsm.v + session_kdf.v · both boards (ROLE = 0 rover, 1 base)

Session setup

At every boot the rover and base agree on a fresh session key K_s from two random nonces, one from each side. Both HELLO messages carry a GMAC tag under the long-term key K, so nobody without K can start or hijack a session, and traffic recorded in an old session fails the tag check in the new one.
